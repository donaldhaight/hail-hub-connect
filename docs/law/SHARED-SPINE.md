# Shared Spine

## Purpose

Freeze the part of the system that should remain stable while the product is rewritten and operated from many different perspectives.

The guiding rule is simple:

> **Change the hat, not the foundation.**

## Shared Spine

The invariant sequence is:

**Interested User → Identity / File → Certification → Roles → Permissions → Ledger → Tasks → Records**

This spine belongs to the platform, not to any single Stakeholder Group, company, brand, or user interface.

## 1. Interested User

The Interested User is the universal front-door state.

A person can arrive anonymously and receive:

- a persistent device anchor;
- a holding wallet;
- an append-only ledger history; and
- a file that can later be claimed by an authenticated identity.

The Interested User does not need to know which future role they may hold.

## 2. Identity / File

When the person identifies, signs in, or accepts an invitation, the existing file is claimed rather than replaced.

The principle is:

**one human → one continuing record**

The identity layer should preserve prior actions, earned value, provenance, approvals, certifications, roles, and future role changes.

## 3. Certification

Operating roles are earned through defined qualification or certification processes.

The initial operating roles are:

- Independent Sales Rep (ISR);
- Licensed Contractor (LC);
- Property Owner (PO) follows as the transaction participant invited into a project.

Certification rules may differ by role, but the certification mechanism should remain shared.

## 4. Roles

A single person may hold multiple roles.

Roles do not create separate people or separate histories.

A role changes:

- what the person may see;
- what the person may do;
- what tasks they receive;
- what approvals they own; and
- which operating area is presented.

The user may switch hats without leaving the shared record.

## 5. Permissions

Permissions are derived from roles and relationships.

The system must distinguish between:

- platform administration;
- Stakeholder Group administration;
- company administration;
- operating roles;
- project-specific authority; and
- record visibility.

Changing the presentation must never bypass the permission model.

## 6. Ledger

The ledger is part of the shared spine.

It records material movements, obligations, certifications, payments, credits, debits, assignments, and other events that require an auditable history.

The ledger should not belong exclusively to the ISR view, LC view, Construction Management view, or Prepare America view.

Those views read the same underlying record according to permission.

## 7. Tasks

Tasks are the operational bridge between roles and workflows.

A task answers:

- what needs to happen;
- who owns the next action;
- what evidence is required;
- what state the work is in; and
- what event closes or advances it.

App Home remains the shared task destination while role-specific operating areas provide the specialized work surfaces.

## 8. Records

Every meaningful workflow produces or updates a record.

For the Construction Management proof of concept, the emerging record includes people, companies, leads, opportunities, projects, claims, contracts, estimates, work orders, invoices, payments, commissions, approvals, documents, evidence, and events.

The exact ClaimExpress object model will be defined from the live RRCA workflow and legacy screens rather than invented prematurely.

## The Hats

The same shared spine can be presented through different operating perspectives, including:

- Interested User;
- ISR;
- LC;
- PO;
- Construction Manager / SiteBMS;
- Founding Sponsor / Stakeholder;
- SAS B platform administration;
- SAS A technology administration;
- Prepare America / Human Blockchain perspectives.

Each hat may have different navigation, dashboards, language, tasks, reports, permissions, and objectives.

The underlying person, identity, ledger, history, relationships, and records remain shared.

## Three Source Systems

Future requirements are being reconciled from three sources:

1. **Original Siteforum / ClaimExpress** — legacy architecture, screens, workflows, legal constructs, Terms of Service, revenue models, and operating knowledge.
2. **Current Lovable codebase** — working front door, authentication, role spine, wallet, ledger, onboarding, certification, permissions, App Home, and emerging operating areas.
3. **Current RRCA operating requirements** — especially the Draft Connecticut Agreement and the real-world requirements of RRCA as Founding Sponsor and first operator of the Construction Management Group.

None of these sources alone defines the final product.

The DH Method is used to reconcile them:

> **Map the real-world need onto proven existing tools, then build only what is missing.**

## Build Rule

Before adding a new screen, table, workflow, or integration, ask:

1. Is this already part of the shared spine?
2. Does the current Lovable application already perform it?
3. Does JobNimbus or another connected platform already perform it?
4. Is it unique to this hat?
5. Is it a SiteBMS requirement, SAS B requirement, SAS A requirement, or ClaimExpress API/MCP requirement?

Only then build.

## Immediate Sequence

The shared spine is now treated as the stable working foundation.

Next, define the hats one at a time, beginning with the live RRCA operating need.

Recommended order:

**Construction Manager / SiteBMS → LC → ISR → PO**

The existing Interested User and ISR/LC onboarding and certification work should remain intact unless the role-by-role walkthrough identifies a concrete reason to change it.
