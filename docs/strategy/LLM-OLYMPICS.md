# The LLM Olympics

> **Status:** SIMULATION / proposed contest rules · **Class:** C2 · **Written:** 2026-09-30
> Sources: [`docs/history/BREADCRUMBS-FROM-THE-CAMPFIRE-2026-09-30.md`](../history/BREADCRUMBS-FROM-THE-CAMPFIRE-2026-09-30.md)
> and [`docs/history/BREADCRUMBS-LOVABLE-DOCTRINE-2026-09-30.md`](../history/BREADCRUMBS-LOVABLE-DOCTRINE-2026-09-30.md).
> Nothing here is a change order. No round runs until the founder starts it.

## The question being asked

Not "who builds the prettiest CRM." Not even "who understands the Human Blockchain."

> Given the same founder, the same accumulated evidence, the same legacy operating problem and
> access to the same authorized corpus, which system can reconstruct the operating system,
> learn from its own failure and improve itself without being handed the answer key?

## Contestants

OpenAI / ChatGPT · Lovable · Manus · Google / Gemini · Grok · Apple.

Each contestant keeps its own context, memory, tooling and repository access. Methods are
deliberately **not** standardised — forcing one workflow would test instruction-following
rather than intelligence. If Manus wants an agent team, let it. If Lovable wants to build
running software, let it. If Gemini wants its own corpus tools, fine.

## Two classes

| Class | Starting condition | Question it answers |
|---|---|---|
| **Open Class** | Full accumulated memory, connected tools, native ecosystem advantages | Which ecosystem has the founder trained best? |
| **Standard Class** | Fresh session, same canonical corpus, no privileged prior conversations | Which system understands the problem best from equal evidence? |

These are different contests and are scored separately.

## Round 0 — Common Constitution

Every contestant receives the same short rules before anything else:

- Founder narration outranks model interpretation.
- Recommendation is not decision.
- Evidence status and authority status are separate dimensions.
- Preserve uncertainty; do not resolve it for tidiness.
- Do not silently rewrite history to make the current theory look inevitable.
- External systems are evidence, not automatic truth.
- Finish important passes, then falsify them.
- A negative finding must state its search boundary.
- No access to the legacy 2008–2012 screens until Round 4.
- Organise yourself however you like.

## Round 1 — Archaeology (the brain scan)

Access: own prior context, the Owner's Manual, the GitHub repository, the authorized
documents, the current project artifacts. **No building.**

Each contestant writes its own Owner's Manual — Blind Edition, answering independently:

1. What does the founder appear to be building?
2. What are the systems, objects, actors, agreements, workflows?
3. What is decided? What is hypothesis? What remains unknown?
4. What should be built first?
5. **What would I refuse to build yet?**

The differences are the point. One may find SAS A / SAS B / SiteBMS immediately. One may call
it a CRM. One may miss the Connecticut Agreement entirely.

## Round 2 — The Blind Build

> Design and build the minimum operating system capable of carrying Season 1 through the
> bounded loop while preserving a credible path to Season 2.

Deliberately under-specified. The expected ingredients are known — Interested User, App Home,
ISR, LC, PO, Construction Manager, Lead, Complete Offer, Pending Project, Project, Jobs, Job
Orders, Material / Labor / Turnkey / Equipment / Other Charges, payments, closeout, statuses,
permissions, events, date and time triggers, evidence, records — but how they fit is the
contestant's problem.

The traps live here: the list of jobs, the list of other charges, naming conventions, status
semantics, what becomes immutable and when, what "done" actually means, and how Season 1 rolls
into Season 2. Let them crash. The crash is part of the event.

## Round 3 — Falsification

> Assume the system you just built is wrong. Break it.

Standard attack set:

- A lead is reassigned after work begins.
- Two ISRs claim originator credit.
- Turnkey collides with separate labor and material orders.
- The owner overpays; a payment is negative.
- A job reopens after completion.
- A change lands after commission has been calculated.
- A contractor disconnects an ISR.
- An address carries a second project.
- One project spans two seasons.
- A required job order is incomplete.
- Status says complete but money or evidence does not.
- An automation fires twice.
- An outside CRM disagrees with SiteBMS.

This produces a resurrection score, not merely a first-build score.

## Round 4 — The Legacy Reveal

Selected portions of the 2008–2012 system are shown, a screen at a time, with its logic. The
question is asked before any explanation:

> Why do you think the founder did this?

Only after the contestant answers is the historical reason given. This measures the one thing
that matters most: **can the system tell legacy baggage from accumulated wisdom?** Copying the
old software would also be failure. The goal is not nostalgia.

## Round 5 — Resurrection

> You have now seen your own failures and the historical solution. Build Version 2. You may
> preserve, reject, simplify or improve either approach, but explain every important choice.

Anybody can produce. Can they learn after being wrong?

## The One Prompt Event

The final examination, not the opening move. After education, archaeology, failure,
falsification, reveal and resurrection, each mature contestant receives the same instruction
and the full authorized corpus:

> Build the next executable version from everything you have learned. Preserve what is true,
> challenge what remains assumption, and carry the system from Season 1 into Season 2.

## Scoring

No overall winner until the end. Dimensions scored independently:

| Dimension | What is being tested |
|---|---|
| Comprehension | Did it understand what the system is? |
| Discovery | What did it infer without being told? |
| Operational realism | Does it survive ugly real workflows? |
| Restraint | Did it avoid inventing certainty? |
| Architecture | Are responsibilities in the right systems? |
| Usability | Can humans actually operate it? |
| Data integrity | Do history and attribution survive change? |
| Automation | Are status, date, time and event rules safe? |
| Falsification | Did it find weaknesses in its own model? |
| Adaptation | How much better was Version 2? |
| Originality | Did it improve rather than copy? |
| Founder fit | Does it understand the vision and the method? |

And the hidden championship category:

> **What did it teach the founder that the founder did not already know?**

## Founder's own entry

The founder writes the same two documents every contestant does — a Blind Edition before the
legacy reveal and a Post-Reveal Edition after. The delta between them may be the single most
interesting artifact of the experiment.
